# ARTEX 금융권 연쇄 해킹 (2026.09–10)

> 2026년 9월 말부터 국내 금융사 16곳이 연쇄 침해되어 개인정보 약 10만 건이 유출됐습니다.
> 공격 인프라에서 AI 자율 침투테스트 도구 **ARTEX**의 흔적이 확인됐습니다.

## TL;DR

- **피해**: 은행·저축은행·캐피탈·온투업·가상자산사업자 등 **16개사, 약 10만 건** (2026-10-14 금융위 발표)
- **표적**: 핵심 뱅킹이 아닌 **외부 노출 주변 시스템** (대출모집인 조회, 직원 업무지원, 외주 웹서버)
- **수법**: 인증·인가가 빠진 조회 기능에 **식별값을 바꿔 가며 반복 조회** (IDOR 열거), IP 차단 시 IP 교체
- **관제 관점 핵심**: 일부 은행은 공격 시작 **42~68시간 뒤** 인지. 시그니처·IP 차단 중심 관제의 한계
- **현황**: 경찰이 10/20 중대범죄로 판단, 공격자 신원은 공식 미확정

## 공격 방식

금융당국이 분류한 세 가지 유형:

1. **정보조회 서비스의 인증 누락**: 본인확인 없이 대출신청 내역 등을 조회 가능. 공격자는 고객번호 등 식별값을 무작위로 대입하며 반복 조회했고, 차단되면 IP를 바꿔 계속함
2. **직원 업무지원 서비스의 접근통제 미흡**: 등록 단말 제한 누락, 권한 없이 접근 가능한 웹 취약점 방치
3. **알려진 취약점 미조치**: 공개 취약점으로 악성코드 설치 후 고객정보가 담긴 로그 파일 탈취

공통점은 **Shadow IT / Shadow API**입니다. 보안팀 관리 목록에서 빠져 있거나 핵심 시스템보다 덜 관리되던 외부 접점에서, 서버가 요청자의 데이터 열람 권한을 검증하지 않는 **BOLA/IDOR** 결함이 악용됐습니다. 데이터베이스에 악성 명령을 주입하는 방식이 아니라 **정상 조회 기능을 반복 호출**했다는 점이 탐지를 어렵게 했습니다.

## ARTEX란

| 항목 | 내용 |
|---|---|
| 정체 | LLM 기반 오픈소스 'AI 자율 침투테스트 시스템' (원래 레드팀 도구) |
| 구조 | 목표 분해(Goals) → 다음 작업 결정(Planner) → 도구 실행(Worker) → 재검증(Retester)을 반복하는 이벤트 기반 루프 |
| 확인된 흔적 | 금융보안원: 공격 IP 역추적으로 흔적 확인 / CrowdStrike: 공격 서버에서 ARTEX 설정 파일, 여러 LLM 사용 기록 발견 |
| 미확인 사항 | 각 공격에서 ARTEX가 어느 단계에 무슨 역할을 했는지, 모든 사고가 동일 공격자인지, 공격자 신원 |
| 현재 상태 | 2026-10-08 개발자가 공개 개발 중단. 이미 배포된 코드는 회수 불가 |

> AI가 새로운 해킹 기법을 만든 것이 아니라, 방치된 기본 허점을 **사람보다 빠르고 넓게** 찾아낸 사례에 가깝습니다.

## 보안관제 관점 분석

### 탐지까지 걸린 시간

| 금융사 | 공격 시작 | 인지 | 소요 |
|---|---|---|---|
| KB국민은행 | 09-27 23:19 | 09-30 19:00경 | 약 68시간 (공격 종료 후 약 25시간) |
| 하나은행 | 09-30 12:16 | 10-02 06:00경 | 약 42시간 (공격 종료 후 약 31시간) |
| 신한은행 | 09-28 18:04 | 09-29 09:30경 | 약 15시간 (최종 차단까지 약 30시간) |

두 은행은 **공격이 끝난 뒤** 사후 점검으로 발견했습니다. 실시간 관제가 작동하지 않은 셈입니다.

### 기존 관제가 놓친 이유

| 원인 | 설명 |
|---|---|
| 정상 요청으로 위장 | 악성 페이로드가 없어 IPS·WAF 시그니처에 걸리지 않음 |
| IP 차단의 한계 | 공유된 공격 IP만 33개(중복 제거 28개), 대부분 프록시·임대 서버. 막으면 다음 IP로 이동 |
| 관제 범위 밖 자산 | 주변 시스템은 SIEM 로그 수집·탐지 룰 대상에서 누락되기 쉬움 |
| 업무 로직 이상 | "한 요청자가 수천 명의 고객 정보 조회"는 애플리케이션 로그에만 남음 |
| AI의 속도·규모 | 일요일 밤 시작, 42시간 이상 지속. 야간·휴일 교대 관제로 대응 곤란 |

### 탐지·대응

상세 탐지 시나리오: [`detection-scenarios.md`](./detection-scenarios.md)
Sigma 룰: [`../detection/`](../detection/)

**대응 플레이북 요약**

1. **격리**: 세션·계정 차단, 필요 시 문제 API·서비스 일시 중단 (IP 차단만으로는 불충분)
2. **범위 확인**: URI·파라미터 패턴, User-Agent, 요청 간격 기준으로 다른 IP 활동까지 역추적
3. **유출 산정**: 응답 로그로 실제 반환된 고객 정보 특정 (조회 대상 식별값 로깅 필요)
4. **공유**: 공격 IP·패턴을 금융보안원 등 유관기관과 신속 공유
5. **근본 조치**: 서버 측 객체 단위 권한 검증 등 개발 단에서 수정

**관제 조직 체크리스트**

- [ ] 외부 접근 가능한 모든 서비스를 관제 대상으로 등록 ("고객용이 아니라서"는 제외 사유가 아님)
- [ ] "누가 어떤 고객 정보를 조회했는가"가 남는 애플리케이션 로그를 SIEM에 연동
- [ ] 공유 IOC 자동 반영 및 과거 로그 소급 검색(retro-hunt) 체계
- [ ] MTTD·MTTR 정기 측정 및 모의훈련
- [ ] 경보 분류·상관분석 자동화(SOAR) 적용

## IOC 관련 안내

- 금감원·금융보안원이 전파한 의심 공격 IP 목록은 이 저장소에 싣지 않았습니다. 대부분 우회용 주소로 재사용·재할당될 수 있습니다. 원문은 [PLURA 2보](https://blog.plura.io/ko/respond/financial-sector-hacking-ioc-artex-2nd-report/)를 참고하세요.
- PLURA가 ARTEX 공개 소스에서 추출한 User-Agent 후보는 [`sigma_artex_user_agent.yml`](../detection/sigma_artex_user_agent.yml)에 반영했습니다. **실제 금융권 공격 로그에서 관측된 값으로 확인된 것은 아니며**, 쉽게 바꿀 수 있으므로 보조 지표로만 사용하세요.
